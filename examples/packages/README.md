# Editable module packages

These editable packages include TypeScript source, license and provenance. Run the
commands below from the repository root after `npm ci`.

| Starter | API | Purpose |
| --- | --- | --- |
| [force](force/) | v1 | Add a force model |
| [numerical](numerical/) | v1 | Replace numerical dynamics |
| [telemetry](telemetry/) | v1 | Add an overlay and instrument panel |
| [state](state/) | v1 | Persist and migrate module state |
| [inventory](inventory/) | v2 | Register versioned authoritative data and commands |

The first four correspond to the local code starters in [examples/modules](../modules/README.md).
More API v2 packages are available in [modules/](../../modules/). Choose a starter
that matches the target game's API and capabilities.

```sh
npm run module:build -- examples/packages/force/module.json /tmp/force.spacemod
npm run module:validate -- /tmp/force.spacemod
npm run module:unpack -- /tmp/force.spacemod /tmp/my-force
# Edit /tmp/my-force/src/main.ts and its module.json (use your own namespaced ID).
npm run module:build -- /tmp/my-force/module.json
npm run module:pack -- /tmp/my-force /tmp/my-force.spacemod
```

In **ModMenu**, choose **Import game, plugin or universe…**, install the `.spacemod`,
then select and apply it in the compatible module configuration. Inspection does not run code. Code runs with
the application's privileges when enabled; use files from authors you trust.

`src/entry.ts` adapts the old example's text-asset names to the new `assets/`
paths. `dist/module.js` and `integrity.json` are generated by `module:build`.
Build before packing; the browser cannot compile TypeScript. The same build can
still produce a v1 `.module.json` for legacy tooling by choosing that extension.
Binary assets travel intact; the v1 asset API exposes only declared text assets.

To create a fresh API v1 module:

```sh
npm run module:new -- local.my-module /tmp/my-module
npm run module:build -- /tmp/my-module/module.json /tmp/my-module.spacemod
```

For API v2, copy `inventory/` or a suitable editable package from `modules/`, then
update its identity and implement its initializer and capability declarations.
The v1 scaffold cannot become a v2 module by changing only the API version string.

A package is ordinary ZIP (stored or DEFLATE) with `module.json`, `integrity.json`,
source, bundle, assets, notices and optional structured Players/Creators guides.
Recompression preserves its identity. Any file edit changes the package identity;
source, assets, notices and compiler inputs require rebuilding before play.

`npm run module:convert -- old/module.json /tmp/portable-copy` uses original source when it
exists. A legacy `.module.json` artifact can be converted too, but is explicitly
marked `legacy-unavailable`: unpacking reveals its bundle and attribution, not
missing TypeScript. Data/universe/shader conversions require `--license-file`
with the author's license text; universes/shaders also require `--license SPDX`.
Converting a file never grants redistribution rights.

`npm run game:build -- game.json output.spacegame` exports an existing v1 game or a v2
unpacked game folder. `npm run game:validate -- output.spacegame` checks every embedded
package and its exact lock without running code. `module:unpack` also opens games;
edit embedded modules with the module commands, then rebuild the outer game.
Legacy gzip/JSON games, multi-plugin packs, profiles, universe files, shader JSON
and source files remain readable. A v2 archive is a file container; executable
modules separately declare API v1 or v2. Game compatibility also depends on its
target selection, host adapter and required providers. Device modules use the
**Device and network modules** configuration; see the in-game Creators Manual.

Setup, content and progress are separate:

| File | Purpose | Archive layout |
| --- | --- | --- |
| `.spacegame` | Game setup and exact selection | `modules/` for code, `data/` for `.spacedata` files |
| `.spacemod` | Executable module and editable source | `module.json`, `src/`, `dist/`, `assets/` |
| `.spacedata` | Reusable definitions, content or shaders | `data.json`, `data/`, integrity; no executable entry |
| `.spaceuniverse` | Saved universe progress | `save.json`, `state/`, definition snapshot under `data/` |

**Save universe** / **Load universe…** are in Fleet. Setup's **Export** exports
universe definitions. Older `.spaceuniverse` definition files and old save JSON
remain readable; contents, rather than extensions, determine their type.

`file:unpack`, `file:pack` and `file:validate` work on any of these ZIP files.
Packing recomputes inventories but still refuses stale code or game locks. Use
`module:build` for source changes and `game:build` for a changed game selection.
`packages/module-tools/portable.schema.json` helps editors check module/data
metadata; runtime validation also checks hashes, sizes and cross-file contracts.

If a recipient cannot inflate raw DEFLATE, export a stored ZIP with
`npm run module:pack -- my-module output.spacemod --store` (or `file:pack`).
It has the same content identity and needs no compression API to read.
