## Requires
Nothing.

## Composition
- Slots: view.prediction
- Dependencies: none
- Conflicts: none
- Initialize before: none; after: none

## Settings
- maxMs: number, default 3, from 0.1 to 16, step 0.1. Prediction work per view (ms): Wall-time ceiling for one tracing update. Guest view overrides can lower their budget; physics and prediction results are unchanged.
- traceSamplesPerSecond: number, default 1000, from 1 to 1000, step 1. Analytic tracing rate (samples/s): Rate at which a progressive coast preview earns sample work. Changes how quickly the complete path appears, not simulation precision.
- numericalSamplesPerSecond: number, default 12000, from 120 to 24000, step 1. Surface/numerical tracing rate (samples/s): Sample-work rate for terrain/contact or numerical previews, still bounded by the work-time ceiling and existing per-update cap.

## SimulationContext
Motion context with an optional numerical/contact replacement and force schedule. All motion is synchronous, body-relative 2D SI: metres, seconds, radians (+Y up). Methods leave input state untouched. Contexts are owned per world/vehicle definition; craft with the same handling share a context. No DOM or timers. Prediction consumers own a clone and dispose it when a job ends or is cancelled.
    export interface SimulationContext {
      readonly modelIdentity: string;
      readonly stepSeconds: 0.01;
      readonly vehicle: Readonly<VehicleDefaults>;
      readonly capabilities: MotionCapabilities;
      readonly services: MotionServices;
      validateState(state: State, body: Body, surface?: SurfaceProfile): void;
      step(state: State, controls: Controls, seconds: number, body: Body, surface?: SurfaceProfile): State;
      advance(state: State, controls: Controls, seconds: number, body: Body, surface?: SurfaceProfile): State;
      predict(start: State, coarse: boolean, body: Body, surface?: SurfaceProfile): Generator<GhostSample, GhostEnd>;
      keplerCoast(state: State, body: Body, surface?: SurfaceProfile, seconds?: number): Coast | undefined;
      coastAt(coast: Coast, time: number, body: Body, surface?: SurfaceProfile, options?: { readonly cache?: boolean }): Propagation;
      coastCacheStats(coast: Coast | undefined): CoastCacheStats;
      /** Same immutable configuration; fresh derived caches and no live mutable state. */
      cloneForPrediction(): SimulationContext;
      /** Release derived caches. Idempotent; the context can rebuild them if reused. */
      dispose(): void;
    }

## FlightPrediction
A progressive trajectory preview for one view. It traces on an isolated motion-context clone (or `world.predictShip` when a world is passed) and never advances live authority. Consumers read `path` and `pathEnd`; the remaining fields are diagnostics. `path` samples are body-relative SI (metres, m/s, seconds of simulation time) in the frame each sample names. Arrays are reused between passes: copy a path you need to keep.
    export interface FlightPrediction extends Disposable {
      pass: PredictionPass | undefined; passKey: string; pathKey: string; passCount: number; path: readonly GhostSample[]; pathEnd: GhostEnd;
      lastPass: PredictionSummary;
      /** Wall-clock milliseconds of tracing work allowed per `update`, from 0.1 to 16. */
      maxMs: number;
      /** Cancel the current pass and clear the path; the next `update` starts a new one. */
      invalidate(): void;
      /** Call once per rendered frame. Starts a new pass when the ship, body, surface, motion
       * model or relevant command epoch changed, otherwise continues the current one within
       * `maxMs`. `seconds` is the elapsed wall time used to earn sample work. Throws after dispose. */
      update(context: SimulationContext, state: State, activeBody: ResolvedBody, surface: SurfaceProfile | undefined,
        selectedShipId: string | undefined, seconds: number, engine: boolean, controls?: Controls, world?: WorldRead): void;

      text(state: State): string;

Initialization is synchronous in Phase 2. Own resources immediately after allocation. provide() only accepts slots selected for this module by the resolved profile.

Typed handle for one service slot and exact version, exported by game-api as a constant (for example `THROTTLE_HUD`). Pass it to `provide`, `use` or `tryUse`; never construct a look-alike key for a service you have not declared in the manifest.       readonly slot: string;
      readonly version: string;
      readonly serviceType?: (value: T) => T;
    }

=== Shared flight plans [spacelab.flight-plans/usage]
A shared service that stores maneuver plans as portable intent and checks them against the selected physics.


## What it does
A flight plan is a list of maneuver nodes for one ship: at an absolute simulation time, add a velocity change made of prograde and radial parts, in m/s, around a named body. This module captures, validates and evaluates those plans. It stores intent only: no throttle, warp, arming or execution state. Evaluation uses the physics the game selected (motion, orbits, surfaces and rails) on a cloned context and never changes the live world.
Planners, transfer search and save files share one plan format, space-sim-flight-plans/1, so a plan made by one tool can be reviewed by another.

## Provides and requires
- Provides flight.plans@1.0.0 through the FLIGHT_PLANS key: a FlightPlanService.
- Requires no services. Callers pass a WorldRead and ship. Finite-burn checks also need a ManeuverBurnFactory, which the host binds with withBurns.
- Consumers in this checkout: spacelab.transfer-planner requires flight.plans@^1.0.0; spacelab.maneuver-editor declares it as optional; the Space Sim host uses it to validate plans stored in saves.

## Settings
This module has no settings.

## Lifecycle
- Initialization provides one frozen, stateless service and this guide. The module owns no resources between calls.
- capture snapshots the ship's current coast, the world identity and its motion model. read validates an untrusted archive: at most 64 plans of 16 nodes, node times increasing and within 100 Julian years of the plan's start. Unknown fields are dropped, and invalid input throws an Error that starts with "Flight plan:".
- evaluate is a fast check for nodes around the starting body. A node on another body, a finite-burn node, or a coast that may cross an SOI or reach the surface first gets a reason asking for progressive evaluation.
- evaluateAsync and predict are generators that do a bounded amount of work per step. They follow coasts through SOI changes and surface contact. They need world.predictionFeatures.futureSeeds, and endTime when a coast has to be traced rather than solved directly; older hosts get a reason instead. Close a generator you stop early with return(): this releases its forecast and cloned motion context.
- Each evaluated node reports valid and a readable reason. A changed universe, system, physics fingerprint or motion model invalidates every node until the player reviews the plan; after the first failure, later nodes repeat its reason.

## Remove or replace
Space Sim enables this module but does not list flight.plans as a required slot. Without it, the transfer planner cannot be enabled because it requires the service, the maneuver editor keeps working without shared plans, and a save that contains flight plans fails to load with a message asking for the module.
A replacement provides flight.plans@1.0.0, lists flight.plans in slots and is selected with "providers": { "flight.plans": "your.module-id" }. It must still read space-sim-flight-plans/1 archives, so that existing saves and other planners stay compatible.

## Stability
Three versions apply here and change independently: the module version 0.1.0, the API identifier space-sim-game-api/2, and the archive format space-sim-flight-plans/1. The API and the manifest format, space-sim-module/2, are pre-freeze. A new archive format would need a migration so that older saves keep loading. Optional members of FlightPlanService, such as evaluateAsync and withBurns, may be missing on older providers; check for them before calling.

## Example
examples/modules/flight-plans declares flight.plans as an optional service. It summarizes an archive when the service is present, reports the validation message when an archive is rejected, and still works when no provider is enabled. Build and check it from the repository root:
    npm run module:build -- examples/modules/flight-plans/module.json /tmp/plan-summary.spacemod
    npm run module:validate -- /tmp/plan-summary.spacemod

=== Progressive flight prediction [spacelab.flight-prediction/usage]
Cancellable trajectory previews that a view can trace a little at a time without touching live flight.


## What it does
A prediction (also called a ghost path) is the future trajectory drawn ahead of a ship. This module creates one preview per view and traces it progressively: each rendered frame does a small, bounded amount of work, so long paths appear over several frames instead of stalling one. Tracing runs on an isolated copy of the motion model, or through the world's own read-only predictor, and never advances the live simulation.
All values are body-relative SI: positions in metres, velocities in m/s and times in seconds of simulation time. Each sample may name its active body (bodyId) and the frame it is expressed in (frameId), a translating, nonrotating frame centred on the starting body. Transform both position and velocity through the system's ephemerides before comparing samples from different frames.

## Provides and requires
- Provides view.prediction@1.0.0 through the PREDICTIONS key: a PredictionFactory whose create(onComplete) returns a FlightPrediction.
- Requires no services. Callers pass the SimulationContext, ship state, body and optional surface on every update, and optionally a WorldRead.
- Consumers in this checkout: the flight host (Player 1's preview), spacelab.flight-split (guest seats) and spacelab.maneuver-editor, which both require view.prediction@^1.0.0.

## Settings
- maxMs (default 3, from 0.1 to 16, step 0.1): wall-clock milliseconds of tracing work allowed in one update of one preview. A consumer may lower FlightPrediction.maxMs for a single preview, for example a split-screen guest. Results do not change, only how quickly they appear.
- traceSamplesPerSecond (default 1000, from 1 to 1000, step 1): samples of work earned per second of elapsed wall time for analytic coast previews.
- numericalSamplesPerSecond (default 12000, from 120 to 24000, step 1): samples of work earned per second for previews that need step-by-step integration, such as terrain contact or shared-world rules.
- Each update allows between 128 and 256 samples of work and stops early when maxMs is used up.

## Lifecycle
- Initialization provides the factory and registers it with context.own, so disposing the candidate disposes every preview it created.
- create(onComplete) returns an independent preview with its own job, budget and two reusable sample buffers. onComplete runs once for each finished pass.
- update starts a new pass when the ship, its status, the body, the surface, the motion model or a relevant command changes; otherwise it continues the current pass. While a replacement is tracing, path shows only the new partial path, never the stale one.
- Pass world to trace through sphere-of-influence (SOI) changes with the host's world.predictShip; omit it for a body-only preview of the given state. In body-only mode, escape means the preview's distance limit was reached.
- Read path and pathEnd. pathEnd is closed (a full orbit), impact, floating, escape, horizon (the predictor's time limit), open (a work limit, never a physical end), failed or grounded. A pass that reaches 32,768 samples ends as open.
- invalidate cancels the pass and clears the path. Cancelling, finishing, a predictor error and dispose all close the job and its cloned context, even if one cleanup step fails. A disposed preview throws on update.
The path array is reused by a later pass. Copy samples you need to keep beyond the next update.

## Remove or replace
Space Sim and Flight starter list view.prediction as a required slot, and split screen and the maneuver editor require it, so those games need a provider. A game that requires none of them can leave prediction out: flight, saves and multiplayer do not depend on it.
A replacement provides view.prediction@1.0.0 with its own PredictionFactory, lists view.prediction in slots, and is selected with "providers": { "view.prediction": "your.module-id" }. It must keep the same rules: no writes to the world, a bounded amount of work per update, and closing every job on invalidate and dispose.

## Stability
Module version 0.1.0 uses API space-sim-game-api/2 and manifest format space-sim-module/2. Both are pre-freeze. FlightPrediction still exposes diagnostic fields such as passKey and lastPass that existing consumers read; treat them as diagnostics that may change before the API freeze.

## Example
examples/modules/flight-prediction consumes view.prediction: it creates a preview, updates it until the pass finishes or a frame limit is reached, copies the result and disposes the preview. Build and check it from the repository root:
    npm run module:build -- examples/modules/flight-prediction/module.json /tmp/prediction-probe.spacemod
    npm run module:validate -- /tmp/prediction-probe.spacemod

=== Throttle HUD [spacelab.throttle-hud/usage]
A per-seat throttle lever that any game can place in its HUD through the hud.throttle service.


## What it does
This module draws the vertical THR lever beside each local player's view. A player drags it, or focuses it and uses the arrow, Page and Home/End keys, to set engine thrust from 0 to 100%. It is an instrument: a small piece of HUD that a HUD owner creates once per seat (one local player) and viewport, then updates every rendered frame. The module reads flight data and sends throttle requests only through an adapter that the game supplies, so it never touches the world, physics or saves.

## Provides and requires
- Provides hud.throttle@1.0.0 through the THROTTLE_HUD key: a HudInstrumentDefinition with ID spacelab.throttle-hud.
- The module itself requires no services. Each lever it creates needs the view.flight-hud-state@1.0.0 adapter (FLIGHT_HUD_STATE), which the game passes to the HUD owner for every seat. A HUD without that adapter skips the lever instead of failing.
- The HUD owner is ui.view-hud@1.0.0 (VIEW_HUD, from spacelab.view-hud). Space Sim and Flight starter select THROTTLE_HUD into every seat's view HUD.

## Settings
- keyboardStepPercent (default 1, from 0.1 to 100, step 0.1): percentage points added or removed by one Up or Down arrow press on a focused lever.
- pageStepPercent (default 10, from 0.1 to 100, step 0.1): percentage points added or removed by one Page Up or Page Down press. Home always selects 0% and End 100%.
- Both settings only change keyboard steps. Session ownership and input locks still decide whether a request is applied.

## Lifecycle
- Initialization provides one shared, stateless instrument definition and this guide. The module owns no resources of its own.
- create runs once per seat. It builds the lever element and its listeners; the first update attaches it to the HUD surface root.
- rebind (a new target, player or session) and cancel stop any drag in progress. A drag also stops when the target ship changes or the adapter reports the lever as locked.
- update runs every frame with wall-clock seconds. It reads the adapter's throttle state and positions the lever; the game may move it with placeThrottle, for example to follow a saved HUD layout. draw adds no overlay shapes.
- dispose removes the element and its window listener. The HUD owner disposes a lever when its seat is removed, when the instrument is deselected, or when one of its methods throws.

## Remove or replace
Space Sim and Flight starter list hud.throttle as a required slot, so their targets need a provider. Players hide the levers with Settings → HUD visibility → Throttle levers, which keeps the module loaded. Physics, saves, the navball, cameras and split screen do not depend on the lever.
To replace it, write a presentation module that lists hud.throttle in slots and provides hud.throttle@1.0.0 with its own HudInstrumentDefinition, then select it in the game profile with "providers": { "hud.throttle": "your.module-id" }. Send thrust only through FlightHudAdapter.setThrottle so that ownership checks still apply.

## Stability
Module version 0.1.0 uses API space-sim-game-api/2 and manifest format space-sim-module/2. Both are pre-freeze: the HUD contracts can still change before the API is frozen, and a breaking change will come with a migration note. The legacy presentation ID builtin.throttle is a compatibility record that keeps the on/off choice in older presentation profiles; new code uses THROTTLE_HUD.

## Example
examples/modules/throttle-hud is a minimal replacement provider: a text readout with − and + buttons that fills hud.throttle@1.0.0. It shows the full instrument lifecycle and reads its step from a setting. Build and check it from the repository root:
    npm run module:build -- examples/modules/throttle-hud/module.json /tmp/throttle-readout.spacemod
    npm run module:validate -- /tmp/throttle-readout.spacemod
